# Name-prefix conventions (CRITICAL — read carefully)

The KashFlow team uses two name prefixes as control signals. Respect them exactly.

- **Single asterisk `*` (e.g. `*Acme Cards`)** = customer has ceased trading. Sync the record but force `hidden=true, status='inactive'`. Keep the `*` prefix in `company_name` so it's still identifiable if someone shows hidden customers.
- **Double asterisk `**` (e.g. `**Acme Cards`)** = active territorial protection. Sync normally. Set `territorial_protection=true`. **KEEP the `**` prefix in `company_name`** — this is how the user identifies them at a glance when sorting alphabetically. Do NOT strip it.
- **No prefix** = normal customer. Sync normally. `territorial_protection=false`.

**WARNING: Dave's `five_minute_customers` pipeline strips prefixes!** When copying from KashFlow, it converts `**` to `*` and removes regional suffixes like `(LD)`. This means `five_minute_customers.Name` is NOT reliable for prefix detection. **Always use the raw `brainbox_candy.customers.Name` field** (joined on CustomerID) for prefix detection and for writing to `company_name` in Supabase.

Detection rules in SQL (MariaDB), using the authoritative raw `customers.Name`:
- `single_asterisk = c.Name LIKE '*%' AND c.Name NOT LIKE '**%'`
- `double_asterisk = c.Name LIKE '**%'`

# Steps

## Step 1 — Determine sync mode

Read Supabase `sync_state`:
- key=`kashflow_customer_last_sync`
- key=`kashflow_customer_last_full_sweep`

- If `last_sync IS NULL` -> **full sweep** (first run ever)
- If today is Sunday AND `last_full_sweep < today's date` -> **full sweep** (weekly refresh)
- Otherwise -> **delta**

## Step 2 — Pull MySQL data

- **Delta mode**: `WHERE fmc.last_updated >= '<last_sync - 1 day>'`
- **Full sweep mode**: no WHERE clause (all ~7,077 rows)

**IMPORTANT: Dave's `five_minute_customers` strips the `**` and `*` prefixes from `Name` (converts `**` to `*`, removes regional suffixes like `(LD)`, etc.). For territorial-protection detection and the canonical `company_name`, we MUST use the Name from the raw `customers` table. Use `five_minute_customers` for EVERYTHING ELSE (geocoding, addresses, phone, etc.).**

Join to `customer_sources` for source name AND to raw `customers` for the authoritative Name:
```sql
SELECT
  fmc.CustomerID,
  fmc.Code,
  COALESCE(c.Name, fmc.Name) AS Name,   -- authoritative name (with ** and * prefixes preserved)
  fmc.Telephone, fmc.Mobile, fmc.Email, fmc.Website,
  fmc.Street_Address, fmc.Street_Address_2_Town, fmc.Town, fmc.Town_County,
  fmc.CountryName, fmc.Postcode,
  fmc.Notes, fmc.Discount, fmc.PaymentTerms, fmc.Created,
  fmc.VATNumber, fmc.EORI, fmc.Member_No, fmc.PO_Number,
  fmc.DeliveryAddress1, fmc.DeliveryAddress2, fmc.DeliveryAddress3, fmc.DeliveryAddress4,
  fmc.DeliveryPostcode, fmc.Store_Type,
  fmc.lat, fmc.lng, fmc.formatted_address,
  fmc.last_updated,
  cs.Name AS source_name
FROM five_minute_customers fmc
LEFT JOIN customers c ON c.CustomerID = fmc.CustomerID
LEFT JOIN customer_sources cs ON cs.ID = fmc.Source
WHERE <delta clause as above>
ORDER BY fmc.Code;
```

For full sweeps, page through in batches of ~200 rows to avoid timeouts.

## Step 6.5 — Refresh proximity conflicts (5 Min Walk cache)

After the main sync is complete and `sync_state` is updated, refresh the cached proximity data in `customers.conflict_kf_code` and `customers.conflict_info`. This keeps the CRM's "5 Min Conflict" column in sync with the latest lat/lng data.

Run these three SQL statements against Supabase in order. The full refresh typically completes in under 5 seconds.

**Step 6.5a — Clear existing conflict cache:**

```sql
UPDATE customers 
SET conflict_kf_code = NULL, 
    conflict_info = NULL 
WHERE conflict_kf_code IS NOT NULL;
```

**Step 6.5b — Populate threat flag for territorial (`**`) customers:**

```sql
WITH territorial AS (
  SELECT id, lat, lng
  FROM customers
  WHERE territorial_protection = true AND lat IS NOT NULL
),
candidates AS (
  SELECT id, kf_code, company_name, lat, lng, status, last_order_date
  FROM customers
  WHERE territorial_protection = false AND hidden = false AND lat IS NOT NULL
),
pairs AS (
  SELECT 
    t.id AS terr_id,
    c.kf_code AS nearby_code,
    c.company_name AS nearby_name,
    c.last_order_date,
    c.status,
    ROUND(111320 * SQRT(
      POWER(t.lat - c.lat, 2) + 
      POWER((t.lng - c.lng) * COS(RADIANS((t.lat + c.lat) / 2)), 2)
    ))::int AS dist_m,
    ROW_NUMBER() OVER (
      PARTITION BY t.id 
      ORDER BY (
        CASE c.status WHEN 'active' THEN 0 WHEN 'dormant' THEN 1 ELSE 2 END,
        POWER(t.lat - c.lat, 2) + POWER((t.lng - c.lng) * COS(RADIANS((t.lat + c.lat) / 2)), 2)
      )
    ) AS rn
  FROM territorial t CROSS JOIN candidates c
  WHERE c.lat BETWEEN t.lat - 0.005 AND t.lat + 0.005
    AND c.lng BETWEEN t.lng - 0.008 AND t.lng + 0.008
)
UPDATE customers cu
SET conflict_kf_code = p.nearby_code,
    conflict_info = jsonb_build_object(
      'company_name', p.nearby_name,
      'last_order_date', p.last_order_date,
      'status', p.status,
      'distance_m', p.dist_m,
      'type', 'threat'
    )
FROM pairs p
WHERE cu.id = p.terr_id AND p.rn = 1 AND p.dist_m <= 417;
```

**Step 6.5c — Populate zone flag for non-territorial customers:**

```sql
WITH territorial AS (
  SELECT id, kf_code, company_name, lat, lng, last_order_date
  FROM customers
  WHERE territorial_protection = true AND lat IS NOT NULL
),
candidates AS (
  SELECT id, lat, lng
  FROM customers
  WHERE territorial_protection = false AND hidden = false AND lat IS NOT NULL
),
pairs AS (
  SELECT 
    c.id AS cand_id,
    t.kf_code AS terr_code,
    t.company_name AS terr_name,
    t.last_order_date,
    ROUND(111320 * SQRT(
      POWER(t.lat - c.lat, 2) + 
      POWER((t.lng - c.lng) * COS(RADIANS((t.lat + c.lat) / 2)), 2)
    ))::int AS dist_m,
    ROW_NUMBER() OVER (
      PARTITION BY c.id 
      ORDER BY POWER(t.lat - c.lat, 2) + POWER((t.lng - c.lng) * COS(RADIANS((t.lat + c.lat) / 2)), 2)
    ) AS rn
  FROM territorial t CROSS JOIN candidates c
  WHERE c.lat BETWEEN t.lat - 0.005 AND t.lat + 0.005
    AND c.lng BETWEEN t.lng - 0.008 AND t.lng + 0.008
)
UPDATE customers cu
SET conflict_kf_code = p.terr_code,
    conflict_info = jsonb_build_object(
      'company_name', p.terr_name,
      'last_order_date', p.last_order_date,
      'distance_m', p.dist_m,
      'type', 'zone'
    )
FROM pairs p
WHERE cu.id = p.cand_id AND p.rn = 1 AND p.dist_m <= 417;
```

Include a count of proximity conflicts refreshed in the narrative summary (Step 7). Example wording: "Proximity cache refreshed: 62 territorial flagged with threats, 253 non-territorial flagged with zones (315 total)."

If any of the three statements error, log to `customer_sync_log.errors` but do NOT fail the overall run. The main customer sync already succeeded — proximity is a secondary derived dataset.

## Step 6.6 — Refresh order / spend figures from invoices

Recompute the six order/spend fields live from `brainbox_candy.invoice` (KashFlow sales invoices) and write them to Supabase `customers`. Run this every time (delta or full sweep) — the rolling 12-month windows move daily, so all invoiced customers need refreshing, not just changed ones.

**Definitions (agreed):** spend is **ex-VAT** (`NetAmount`); quotes are excluded (`quote = 0`); credit notes net off naturally (they are negative `NetAmount`); rolling windows are anchored to the run date (`CURDATE()`); future-dated invoices are excluded from `last_order_date` but otherwise included in totals.

**IMPORTANT — work entirely through MCP SQL calls and in memory. Do NOT write query results to disk, do NOT create or edit any files, and never touch anything under `~/.claude` or other system paths. If a tool offers to save a large result to a file, decline — instead page the data in small batches as below.**

**Step 6.6a — Pull the aggregate from MySQL in pages.** Join `invoice` to the raw `customers` table to resolve the KashFlow `Code` (this maps ~4,166 of 4,170 invoiced customers; `five_minute_customers` misses ~447 so do NOT use it here). Fetch in pages of **500 rows** ordered by `kf_code` using `LIMIT 500 OFFSET n`, and process + write each page (Step 6.6b) before fetching the next — so no single result set is ever large. The aggregate query (add `LIMIT/OFFSET` per page):

```sql
SELECT c.Code AS kf_code,
  COUNT(*) AS invoice_count,
  ROUND(SUM(i.NetAmount),2) AS all_time_spend,
  MIN(i.InvoiceDate) AS first_invoiced,
  MAX(CASE WHEN i.InvoiceDate <= CURDATE() THEN i.InvoiceDate END) AS last_order_date,
  ROUND(SUM(CASE WHEN i.InvoiceDate >= DATE_SUB(CURDATE(), INTERVAL 12 MONTH) AND i.InvoiceDate <= CURDATE() THEN i.NetAmount ELSE 0 END),2) AS last_12m_spend,
  ROUND(SUM(CASE WHEN i.InvoiceDate >= DATE_SUB(CURDATE(), INTERVAL 24 MONTH) AND i.InvoiceDate <  DATE_SUB(CURDATE(), INTERVAL 12 MONTH) THEN i.NetAmount ELSE 0 END),2) AS prior_12m_spend
FROM invoice i
JOIN customers c ON c.CustomerID = i.CustomerID
WHERE i.quote = 0 AND c.Code IS NOT NULL AND c.Code <> ''
GROUP BY c.Code
ORDER BY c.Code;
```

**Step 6.6b — Write to Supabase.** For each batch, update `customers` by `kf_code` using a single VALUES join (batches of ~500). Only the six fields plus `updated_at` are written — never touch any other column here.

```sql
UPDATE customers AS c SET
  invoice_count   = v.invoice_count,
  all_time_spend  = v.all_time_spend,
  first_invoiced  = v.first_invoiced,
  last_order_date = v.last_order_date,
  last_12m_spend  = v.last_12m_spend,
  prior_12m_spend = v.prior_12m_spend,
  updated_at      = now()
FROM (VALUES
  ('BRIC01', 16, 1349.54, DATE '2013-01-16', DATE '2026-04-21', 408.84, 0.00)
  -- ...one row per customer in this batch...
) AS v(kf_code, invoice_count, all_time_spend, first_invoiced, last_order_date, last_12m_spend, prior_12m_spend)
WHERE c.kf_code = v.kf_code;
```

Notes:
- Customers with **no** invoices are simply not in the aggregate; leave their existing values untouched (do not zero them).
- This step refreshes figures only; it does NOT recompute `status` (active/dormant). If a spend-based status recalc is wanted, treat it as a separate task.
- Count how many customer rows were updated and include it in the Step 7 narrative, e.g. "Order figures refreshed for 4,166 customers from live invoices."
- If MySQL is unreachable for this step specifically, log to `customer_sync_log.errors` but do NOT fail the overall run — the customer-detail sync already succeeded.

## Step 6.7 — Refresh reorder call-list fields (Ordered pipeline customers)

The dashboard "Reorder Call List" chases customers in the **Ordered** pipeline stage who have not ordered in 5+ weeks. It anchors on `last_invoice_date` — the customer's latest invoice **regardless of paid/unpaid status** — so a freshly-raised, still-unpaid order resets the reminder. It also shows a direct KashFlow link via `last_invoice_number` / `last_invoice_permalink`.

Run this **every time** (delta or full sweep). It is deliberately scoped to ONLY the customers currently in the Ordered stage — a tiny set (usually a handful) — so it always completes and stays reliable even if Step 6.6's big paged refresh is throttled or truncated. These three columns are routine-managed here and nowhere else.

**Step 6.7a — Get the Ordered customers from Supabase:**

```sql
SELECT kf_customer_id
FROM customers
WHERE pipeline_stage = 'Ordered' AND kf_customer_id IS NOT NULL;
```

If none are returned, skip this step.

**Step 6.7b — For those CustomerIDs, get each one's latest non-quote invoice from MySQL** (any paid status; if several share the latest date, take the highest InvoiceNumber):

```sql
SELECT i.CustomerID, i.InvoiceNumber, i.InvoiceDate, i.PermaLink
FROM invoice i
JOIN (
  SELECT CustomerID, MAX(InvoiceDate) AS maxd
  FROM invoice
  WHERE COALESCE(quote,0)=0 AND CustomerID IN (<ids from 6.7a>)
  GROUP BY CustomerID
) m ON m.CustomerID = i.CustomerID AND m.maxd = i.InvoiceDate
WHERE COALESCE(i.quote,0)=0 AND i.CustomerID IN (<ids from 6.7a>)
ORDER BY i.CustomerID, i.InvoiceNumber DESC;
```

**Step 6.7c — Write back to Supabase** (match by `kf_customer_id`):

```sql
UPDATE customers AS c SET
  last_invoice_date      = v.inv_date,
  last_invoice_number    = v.inv_number,
  last_invoice_permalink = v.permalink,
  updated_at             = now()
FROM (VALUES
  (9659402, DATE '2026-06-26', 70323, 'https://api.kashflow.com/...')
  -- one row per Ordered customer returned in 6.7b
) AS v(kf_id, inv_date, inv_number, permalink)
WHERE c.kf_customer_id = v.kf_id;
```

This guarantees the reorder reminder clears as soon as ANY new order (paid or unpaid) is raised in KashFlow, with the 5-week cycle restarting from the new order date. Ordered customers with no `kf_customer_id` keep `last_invoice_date` NULL, and the call list falls back to their `last_order_date`. Include a line in the Step 7 narrative, e.g. "Reorder fields refreshed for 3 Ordered customers."

- Never retry destructive operations. Log and move on.
